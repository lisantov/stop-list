# Stop List

Управление стоп-листом меню ресторана. Приложение показывает позиции меню, позволяет ставить их в стоп-лист и снимать с причина и сроком, а также редактировать уже остановленные позиции.

---

## Установка и запуск

```bash
npm install
npm run dev      # http://localhost:3000
```

Доступные команды:

| Команда            | Описание                        |
| ------------------ | ------------------------------- |
| `npm run dev`      | Development-сервер с HMR        |
| `npm run build`    | Production-сборка               |
| `npm run start`    | Запуск production-сборки        |
| `npm run lint`     | Проверка ESLint                 |

## API

| Метод   | Путь                       | Описание                                                | Код ошибки |
| ------- | -------------------------- | ------------------------------------------------------- | ---------- |
| `GET`   | `/api/menu-items`          | Список позиций; фильтры `?shop=` и `?status=`         | 400        |
| `POST`  | `/api/menu-items/:id/stop` | Постановка / редактирование стопа (upsert)             | 400, 404, 500 |
| `POST`  | `/api/menu-items/:id/resume` | Снятие со стопа                                       | 400, 404, 409, 500 |

Контракт ошибок: `{ error: string }`.

---

## Валидация

| Поле          | Правило                                                                                   |
| ------------- | ----------------------------------------------------------------------------------------- |
| Причина стопа | Обязательно; одно из четырёх значений: `out_of_stock`, `equipment`, `quality`, `menu_change` |
| Срок стопа    | Пусто = до конца смены (`null`); либо время строго в будущем, не позже чем через 24 ч, шаг 15 минут |
| Остаток       | При `stock = 0` снятие со стопа запрещено (кнопка заблокирована с подсказкой)                |

Валидация проверяется на клиенте (при потере фокуса и при отправке формы) и на сервере перед изменением данных.

## Оптимистичное обновление и симуляция ошибок

### Поведение при ошибках

- **~20 % запросов к мутациям (POST)** случайным образом возвращают ошибку 500 — это задумано для демонстрации оптимистичного отката.
- При ошибке сервера: оптимистически изменённая строка **откатывается без перерендера всего списка** (точечный откат по `id`), а в правом верхнем углу появляется **тост** с текстом ошибки.
- Множественные мутации по одной позиции (двойной клик) **дедуплицируются** — второе нажатие блокируется до завершения первого запроса.

### GET

- `GET /api/menu-items` получает **задержку 600 мс** для отображения skeleton-загрузки на клиенте.
- На время загрузки UI показывает скелетон, при ошибке — сообщение с кнопкой «Повторить».
- Фильтры добавлены в URL через `router.push` — кнопка «Назад» возвращает предыдущие параметры фильтрации.

### Таймзоны

Клиент конвертирует `datetime-local` в UTC-ISO в браузере (локальный часовой пояс пользователя); сервер передаёт ISO без повторной интерпретации. Это гарантирует корректное время даже если клиент и сервер находятся в разных часовых поясах.

## Слои и граница серверного и клиентского кода

Код поделён на четыре слоя: `src/app` (роутинг, layout, API-роуты), `src/features` (фича стоп-листа: клиентские компоненты + модель), `src/shared` (переиспользуемые компоненты UI, схема валидации, `fetcher`, утилиты) и `src/server` (симуляция сети и in-memory store).

**Граница сервер/клиент проходит через `page.tsx` → `StopListContainer`:**
- `src/app/page.tsx` — серверный компонент: читает `searchParams` (это `Promise` в Next 16), валидирует их `isShop`/`isStatusKind` и передаёт примитивы `shop`/`status` в видимый клиентский компонент. Никаких данных и хуков на сервере.
- `StopListContainer.tsx` (`"use client"`) — точка входа в клиент: TanStack Query тянет данные, состояние UI (модалка, «сохраняется», тосты) живёт в Zustand, мутации делают оптимистичные апдейты.
- Валидация формы (`stopItemSchema` из `src/shared/schemas`) — **общая**: вызывается в route handler 'ах на сервере перед изменением данных и в React Hook Form на клиенте.
- Бизнес-логика данных — в `src/app/api/**` (серверные route) через `src/server/menu-store`; клиент трогает данные только через `fetcher` к API.

## Архитектурные решения

1. **Оптимистичное обновление** сделано в мутациях, а не в UI-компонентах: `onMutate` обновляет кэш TanStack Query, `onError` откатывает **только затронутую позицию по `id`** (не весь список) и показывает тост. Снапшот берётся по всем вариантам фильтров, поэтому откат не зависит от активного фильтра и не ломает живую оптимистику других мутаций.
2. **Один источник истины для валидации** — Zod-схема лежит в `src/shared` и используется и на клиенте (RHF), и на сервере (route handlers): правила «причина обязательна», «срок в будущем ≤ 24 ч, шаг 15 мин» гарантированно совпадают и не расходятся.
3. **Фильтры через URL (`router.push`)**, а не локальное состояние: параметры `?shop=`/`?status=` валидируются серверной страницей, сохраняются в истории браузера (кнопка «Назад» работает) и переживают перезагрузку.
4. **UI-состояние вынесено в Zustand** (модалка, toasts, признак «сохраняется»), а сетевые данные — в TanStack Query: это разделяет мгновенный UI от данных с сервера и упрощает откат/инвалидацию.

## Что доделать или переделать, если бы было ещё время

- **Заменить in-memory store** на настоящую персистентность (БД или файл с транзакциями) — сейчас данные после рестарта возвращаются к seed, а мутации конкурентно мутируют общий массив.
- **Покрыть тестами** API-роуты (валидацию, `stop`/`resume`, симуляцию 20 % отказов) и оптимистичный откат (например, Playwright: замер списка до/после ошибки).
- **Доделать доступность модалки**: фокус-трап, закрытие по `Escape`, восстановление фокуса при закрытии; сейчас закрытие только по клику на фон.
- **Авторизация и роли** (овнер/кухня/бар) и история изменений позиций (аудит «кто и когда снял с продажи»).
- **Улучшить UX выбора времени**: компонент-пикер с подсказкой ближайшего валидного слота вместо `datetime-local`.
- Вынести процент отказов в конфиг и **записывать демонстрационные сбои в серверный лог**, чтобы поведение можно было воспроизвести.
